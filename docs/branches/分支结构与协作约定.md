## 3. 共享文件怎样协作

以下文件跨模块共用，修改时应在 PR 中说明调用方影响，并与相关模块共同确认：

- `apps/api/src/app.module.ts`、`apps/web/src/App.tsx` 与统一 API 客户端。
- `packages/shared/src/index.ts`、接口与数据约定、公共错误结构和身份上下文。
- `apps/api/src/b/controllers.ts`、`b/validation.ts` 以及公共配置。
- `TripDetail.tsx`、`TripTools.tsx` 等承载多个功能的容器；只改自己负责的功能块，避免整文件覆盖。
- `apps/api/migrations/`、根 `package.json`、lockfile、CI 和公共样式。

数据库变更新增唯一编号迁移，不重写团队已合并的迁移。功能分支提出接口字段变更时，同步共享类型、实现、调用方和测试。`test` 分支可以暴露接口差异，不能自行修改预期来掩盖业务问题。

## 4. 日常提交与合并

从最新 `main` 出发，在对应功能分支提交；需要整合时向 `main` 发起 PR。一个 PR 尽量聚焦一个功能，描述变更、涉及接口、验证结果及未完成项。PR 合并后保留长期功能分支，并将新的 `main` 正常合并回分支继续工作。

不要将本轮完整版本重新从旧成员分支覆盖回 `main`。旧分支的独有新增工作需先比较差异，再通过新模块分支迁移需要的提交或修改，避免旧代码重新覆盖整合版本。

测试继续执行测试先行原则：先提交对应失败测试，再改实现，阶段比例来自真实结果。本次只整理分支，未运行原来的 222 项测试，也未把 `integration-2` 的功能改动写成新的 0%/100% 结果。

会议材料只记录真实发生的讨论，不补造历史出席人、决策或测试结论。使用 [会议记录模板](../meetings/会议记录模板.md)，记录决定影响的模块/分支、负责人、截止日期和验收方式。
