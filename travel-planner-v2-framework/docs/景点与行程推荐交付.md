## 当前职责与范围

## 推荐规则

- 按兴趣匹配数优先，再参考游玩时长，最后按景点ID稳定排序；每个景点返回匹配主题和理由。目录暂无对应兴趣时明确提示未匹配，不编造推荐依据。
- “按兴趣与天数补充推荐景点”保留用户已选项，逐个尝试可容纳的推荐项。
- 行程优先将同一行政区景点分在一起；不声称最短路线或最优解。
- 八达岭、慕田峪、居庸关等长城景点单独一天；住宿往返交通尚未计算。
- 与统一契约对齐：轻松10:00、480分钟预算、最多2处、休息30分钟；经典09:00、540分钟、最多3处、休息15分钟；充实08:00、600分钟、最多4处、休息10分钟。全部最晚18:00结束，前端预算读取同一paceSettings。
- 同区步行/公共交通/驾车分别预留30/25/20分钟，跨区预留90/60/45分钟。这些是固定规划假设，不是距离或实时查询结果。首站交通为0/none，仅表示未计住宿出发段。
- 每个日期都返回一个day；每个已选景点恰好落入安排或未安排集合。超出容量的景点列入 unassignedPlaceIds，提示增加天数或减少景点，禁止静默丢弃或保存不完整方案。

前端展示参考开始时间。移动日期、调整顺序后重新计算；若超出容量，会提示待调整景点并阻止完整提交。异步推荐期间修改输入，会忽略旧结果并要求重新生成。

## HTTP 接口

以下均需已有 Bearer token，路径前缀 /api。

| 接口                            | 用途                                                                                 |
| ------------------------------- | ------------------------------------------------------------------------------------ |
| POST /recommendations/places    | {cityId,themes,pace} → {items:[{placeId,score,matchedThemes,reasons}],source:'rule'} |
| POST /recommendations/itinerary | 完整 PlanningInput → Proposal，HTTP200；不修改Trip                                   |
| GET /recommendations/:id        | 按用户读取方案，含有效期检查                                                         |
| POST /trips/:id/apply-proposal  | {expectedRevision,proposalId} → planned Trip，HTTP200                                |
| PUT /trips/:id/schedule         | {expectedRevision,days} → 更新正式行程的每日安排                                     |

Proposal 含 proposalId/inputSnapshot/generatedAt/expiresAt/days/unassignedPlaceIds/warnings/source。服务端另外关联 ownerId，默认30分钟有效，存入 PostgreSQL recommendation_proposals；重启后可继续读取。

确认时服务端读取可信方案，检查归属、有效期、输入快照、完整性和日程合法性，并在行程事务内按 revision 更新。只接受 proposalId，不接受客户端伪造方案JSON。过期410、他人/不存在404、输入不匹配409、未安排422；已有planned需先明确重置。

手动日程需覆盖全部日期和已选景点，顺序连续、不重复、不重叠且在预算内；远郊景点不能混在同一天。当前没有地图提供商，手动请求不得把交通标为provider。增删已保存行程的景点或改变规划条件，仍须按既有契约明确重置为草稿后重新生成。

## 前端集成

`NewTripPage` 新增可选 onGenerateProposal(draft):Promise<Proposal>；未注入时直接用相同规则本地预览。原 onBack/onSaveDraft/onComplete/initialState/storage 保留。

`trip-draft-client.ts` 扩展 recommendPlaces/generateProposal/getProposal/applyProposal/updateSchedule。`recommendation-flow.ts` 提供 createRecommendationFlow(api,initialTrip?)，返回三个可直接传给页面的回调，以及 getCurrentTrip()。

```tsx
const api = createTripDraftApi({ getAccessToken });
// 在父级稳定创建一次，切换行程时才新建，避免丢失已保存的ID/revision。
const flow = createRecommendationFlow(api);
<NewTripPage
  onBack={returnToTripList}
  onSaveDraft={flow.onSaveDraft}
  onGenerateProposal={flow.onGenerateProposal}
  onComplete={flow.onComplete}
/>;
```

该适配器串起草稿保存→服务端方案→确认→保存人工排序。每次保留服务端返回版本；确认后日程更新失败，重试只更新已planned行程，不重复创建。不会自动覆盖冲突或自动确认重置。

## 替换接口

- TripCatalog.getCityPlaces/assertCityExists/assertPlacesBelongToCity：由 PlacesModule 统一注入，未来替换为景点数据库或地图目录。
- ProposalReader.getOwnedProposal：供行程模块查询方案，保持推荐与行程业务解耦。
- ProposalRepository：持久化方案；默认PostgreSQL，测试替身不用于正式预览。
- RecommendationClock：有效期时钟，测试可固定。

本次不实现地图路线提供商、逆地理编码、景点管理后台或LLM服务。
