# 联调与验收说明

## 1. 当前可以运行什么

现有工程可运行 API 健康检查、前端 API 状态页，以及 B 的目录、规则推荐、方案存储与地图/可选模型适配测试。B 已提供开发种子 `npm run db:seed:b` 和真实 PostgreSQL 测试 `npm run test:integration:b`；C/D 业务接口、前端业务页和联合业务流程仍待实现。B 的正式业务入口默认要求 C 接入真实认证。

统一静态样例在 [examples](examples/README.md)。它们给出测试材料，不提供服务器。以下“联合业务验收”仍是全员完成标准，不能用 B 的测试替身结果代替；B 实际已验证的范围见 [验证记录](验证记录-B.md)。

## 2. 准备本地环境

当前 B 环境使用服务器 Docker 数据库，本地通过 `npm run db:tunnel:b` 建立 SSH 隧道；具体连接、测试和服务器状态检查见 [服务器开发与测试](服务器开发与测试.md)。以下为其他成员自行准备环境时的通用步骤。

四个人各用自己的工作目录和环境文件。单机开发仍沿用 Web 5173、API 3000；同一电脑需要同时运行多套时，用各自目录、数据库与不冲突端口，显式设置 PORT、CORS_ORIGIN 和 Vite 端口。四个人在不同电脑无需为了区分成员强制改成四组端口。

根目录已有命令：

```powershell
npm ci
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
npm run dev:web
```

API 需要有效的 DATABASE_URL 配置才能启动；数据库不可用时 health 可以为 200、ready 为 503。只看 health 不能判定业务可用。需要运行持久化业务时，先准备 PostgreSQL，再执行：

```powershell
npm run db:migrate
npm run db:migrate:status
npm run dev:api
```

前后端在两个终端启动，或用根目录 `npm run dev` 同时启动。数据库可自行安装或执行 `docker compose up -d postgres`；Docker Desktop 引擎必须已经启动。此前验证没有跑通真实 PostgreSQL/整套 Docker，不把这些命令的存在当成运行成功。

## 3. 三种测试分别记录

| 测试           | 依赖                                               | 能证明什么                          | 不能证明什么                         |
| -------------- | -------------------------------------------------- | ----------------------------------- | ------------------------------------ |
| 单模块模拟测试 | 内存目录/仓库、假外部服务、测试身份                | 参数分支、算法、页面交互、调用约定  | 真正登录、SQL、事务和真实地图可用    |
| 本地集成测试   | 真实测试库、迁移、模块装配、可控外部替身           | SQL、约束、数据隔离、模块协作和回滚 | 第三方账号配额、真实网络与部署稳定性 |
| 联合浏览器验收 | 完整 API、真实数据库、前端、图片存储；地图按需配置 | 用户实际可完成两条流程              | 不代表所有异常和边界都自动覆盖       |

测试输出必须说明哪些依赖为真实、哪些为替身。HTTP 测试注入身份不能被记为真实登录通过；内存事务替身不能被记为 PostgreSQL 回滚已验证。

### 测试脚本的放置

已有 `npm test` 只构建 API，再运行 `apps/api/tests/*.test.cjs`，基础测试无需外部 PostgreSQL。各模块的快速单测继续放该目录；依赖真实数据库的测试放 `apps/api/tests/integration/`，不加入默认快速测试的文件匹配。

B 已提供独立的 `test:integration:b` 脚本，读取 TEST_DATABASE_URL，拒绝空连接和不以 `_test` 结尾的数据库名；在专用库的随机 schema 中创建、测试并清理自己的数据。全员共用的 `test:integration` 仍由 C 后续协调，不要直接在日常开发库运行清空或重建操作。

推荐本地数据库名：`travel_planner_b_test`、`travel_planner_c_test`、`travel_planner_d_test`。每个人运行迁移与种子数据到自己的库；联调另用 `travel_planner_integration_test`。仅修改名称不能自动建库，需先创建并配置权限。

## 4. 四人接口交接顺序

### 第一次：固定契约与替身

- A：给出统一客户端的方法签名和假客户端入口，加载共同示例。
- B：交付地点列表、PlanningInput、Proposal 与 ProposalReader 的首版实现和测试替身。
- C：交付身份上下文、错误格式、校验方式、草稿结构和 revision 规则。
- D：交付 FootprintMap 的 props 和回调、足迹/随笔/媒体示例。

完成条件：四个人使用同一组资源 ID、日期和主题编码，各自小范围测试无需等待其他模块实现。

### 第二次：接通旅行规划

按“登录 → 选城市 → 草稿 → 日期/偏好/景点 → 推荐 → 确认保存 → 重新读取”的顺序接通。B 负责方案，C 负责正式行程，A 负责每一步界面与失败反馈。先不启用模型或真实路线也能用明确标注的规则方案验收。

### 第三次：接通地图手账

D 使用共同身份和地点目录；A 接到访表单、地图组件、图片与随笔页面。验证真实到访才点亮，以及删除/筛选后的数据一致性。图片必须真实上传和读取，示例媒体元数据不算图片上传完成。

## 6. 合并与回归

工程位于外层 Travel-Planning-Assistant Git 仓库内：A、B、C、D 使用各自功能分支，小步提交，不用整个文件夹覆盖别人的成果。

交付前包含：

1. 改动目录与接口清单，迁移和新增配置说明。
2. 本人可复现的启动/测试命令、所用数据库和替身说明。
3. 成功与失败各一组请求响应，关键页面/地图截图。
4. 已通过与未验证项，尤其是真实外部 API、数据库和图片存储。

全员保持已有检查通过：

```powershell
npm run lint
npm run typecheck
npm run build
npm test
npm run format:check
```

仅修改文档时检查格式、链接和示例一致性即可，不要求为了文档变更重复执行所有业务测试。修改公共接口、身份、数据库或模块装配后必须跑相关回归；合并到集成版本再执行两条浏览器流程。

## 7. 验证记录模板

每人可新增 `docs/验证记录-A.md` 等文件，填写实际结果：

```text
模块 / 代码版本：
测试日期 / 执行人：
启动与测试命令：
真实依赖：
测试替身：
通过的用例编号与证据：
失败或未验证的用例：
交给其他成员的接口 / 组件 / 迁移：
```

“未验证”不写成“通过”；阻塞接口可先使用约定替身继续本模块开发，同时记录等待对接的事项。
