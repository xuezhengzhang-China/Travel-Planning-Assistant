# C：行程业务与基础后端开发说明

## 1. 你的交付

负责四步表单背后的保存、校验和正式行程，以及大家共用的身份认证、运行时参数校验、错误格式和迁移协调。A 做截图界面；你不必另做一套前端，也不重复编写 B 的推荐算法。

先读 [接口与数据约定](接口与数据约定.md)。已有 ConfigModule、DatabaseModule、createApp 和基础测试可复用；现有 users 表还没有密码字段，trips 表也没有完整业务字段。

## 3. 先交付公共能力，避免阻塞其他人

1. 给出当前用户上下文形状，例如 `{ userId }`，由服务端验证 token 后构造。对 B/D 提供身份 Guard 的使用示例和测试替换入口。
2. 在统一入口接好运行时 DTO 校验与业务异常转换，采用契约里的 code/message/details。不要假定只写 TypeScript interface 就能验证 HTTP 请求。
3. 实现注册、密码哈希和登录。认证依赖的库、配置与测试随实现一起提交，不能储存明文密码。
4. 维护公共数据库模块，不修改其他人的表字段。所有查询参数化，所有多表写入使用同一事务连接。
5. 汇总 B/D 的增量迁移和模块注册，向 A 提供可测试的登录与草稿接口。

B/D 在你完成前可用测试 provider 注入 actor，不能在公共 HTTP 接口接收一个 `userId` 就当作登录。测试替换只在测试入口生效，正式 AppModule 不注册它。

## 4. 行程最小开发顺序

1. 创建草稿、个人列表和详情；验证只读写自己的数据。
2. 保存日期、主题、节奏、交通方式和选择。空日期只允许成对为空；生成条件完整性由 B 生成入口再次检查。
3. 给行程增加 revision、status，所有变更带 expectedRevision；新建为 1。更新语句的 WHERE 或行锁必须参与版本保护。
4. 通过 B 的 ProposalReader 读取方案，完成确认保存。单测先用假 Reader，不等待外部 API 或大模型。
5. 实现 planned 的手工换日/排序。日期、景点集合、时长、交通和时间不重叠需要重新验证。
6. 实现条件变化时的明确重置，以及删除行程。不得因改日期直接静默清空用户编辑。

## 5. 事务如何组织

确认方案的建议流程：

1. 验证登录身份，按当前用户读取方案并检查有效期。不得向未授权用户先返回“方案过期”。
2. 开启数据库事务，按行程 ID 与 owner_id 读取并锁定行程，或使用等效的原子版本更新。
3. 检查 expectedRevision、draft 状态、输入快照匹配、无未安排项，以及每个日期/景点的完整性。
4. 写入 trip_days 和 trip_items，更新 trips 为 planned，revision 加 1。
5. 全部成功提交，失败回滚；错误不能留下半套日程。返回提交后的 Trip。

若方案仓库在事务外读取，C 应保存其不可变快照并在最终提交前按当前时钟重查有效期。方案内容生成后不可原地修改；重新生成创建新的 proposalId。不要在持有行锁时调用慢速外部地图或模型服务。

其他行程写入同样保护版本。若连接内已开始事务，repository 接收该事务 client，不偷偷回到全局 query。两次相同 revision 的并发写入必须只有一次成功。

## 6. 数据库范围

你负责 users 凭据扩展、trips 的城市/状态/版本/偏好等字段，以及 trip_selections、trip_days、trip_items。城市和景点 FK 依赖 B 的表；初始 trips 的可空日期先保留以支持草稿。

推荐条件可作为结构化字段或受验证的配置数据存储，但已选景点和每日日程使用独立表与约束。删除行程清理其选择和日程，不关联删除 D 的真实到访记录。trip_members 首期保留但不启用协作授权。

迁移协调：C 的身份扩展与 B 的目的地目录先合并，再推荐/行程，最后 D 的足迹和媒体。每个文件使用唯一时间戳；在空测试库完整迁移，并验证旧基础库可向前升级。不能只在自己的已有数据库上手工补列后认为迁移完成。

## 7. 独立测试怎么做

| 层级           | 依赖替换                                        | 验证内容                         |
| -------------- | ----------------------------------------------- | -------------------------------- |
| Service 单测   | 假身份、假 ProposalReader、假地点目录、测试仓库 | 业务分支、错误与调用顺序         |
| HTTP 测试      | createApp 或测试装配、仅测试用身份 provider     | 参数校验、认证、状态码与错误格式 |
| 数据库集成测试 | 独立 PostgreSQL 测试库、真实仓库与迁移          | SQL、约束、回滚、原子版本更新    |

只用假数据库无法证明真实事务与并发行为。至少准备两个测试用户，固定演示 UUID 见 [统一示例](examples/README.md)，实际插入用户时使用测试密码哈希，不把 JSON actor 当作真实登录账号。

重点场景：

- 同日为 1 天、结束早于开始拒绝、无效日期拒绝、超过 30 天拒绝。
- 草稿刷新读取一致；跨城市景点和重复选择拒绝。
- 修改 planned 条件未确认返回 409，确认后清空安排且 revision 只增加一次。
- 推荐输入不匹配、过期、来自他人、存在未安排项均不落日程。
- 写第二条 item 失败时，第一条与状态更新全部回滚。
- 两个请求使用相同 revision 并发提交，恰好一个成功，另一请求 409。
- 他人读取、修改、确认或删除返回 404；不能先泄露内容再在前端隐藏。
- 删除行程后 D 的到访和手账仍然存在。

## 8. 现有命令与交付

从根目录运行：

```powershell
npm test
npm run lint
npm run typecheck
npm run build
```

真实数据库测试应使用单独数据库，例如 `travel_planner_c_test`，并让测试入口明确读取该连接；不要在个人日常数据库执行清空表操作。当前没有业务 seed 或 test:integration 脚本，增加时补文档和测试数据库保护，禁止伪称已有。

交付时提供身份接入示例、迁移顺序、草稿与确认保存请求示例、业务测试命令和两用户验证记录。你协调公共文件，但 B/D 仍要为自己的功能编写测试，不把全部测试工作集中到你这里。
