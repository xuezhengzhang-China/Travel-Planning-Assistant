### 4.2 真实 HTTP 与 PostgreSQL

通过实际注册、登录并调用随机端口 API，创建独立测试用户，结束只清理本次用户及其数据：

1. 创建草稿，保存日期、六类偏好与景点；SQL 核实内容及版本。
2. 通过真实推荐接口生成规则方案，写入 PostgreSQL。
3. 退出 API 进程并启动新进程；草稿、列表与方案可恢复，旧版本写入被拒绝。
4. 确认方案为 planned，人工修改日程，再次重启读取一致。
5. 核实关系表内容；强制第二条重复选择写入失败，标题、版本及原日程整体回滚。
6. 同版本并发写入只有一个成功，另一个返回 409。
7. 第二用户不能读取或删除第一用户行程，返回 404；旧版本删除返回 409。
8. 正确版本删除返回 204，后续读取 404，行程选择与安排子表被清理。

这是进程退出重启后的数据库持久化验证，未重启 Windows、Docker 或 PostgreSQL 服务。

## 5. 当前行程如何生成

当前为共享规则引擎 `packages/shared/recommendation-engine.cjs`，不是调用大模型生成。数据库提供景点类别、行政区、建议游玩时长及远郊标记；引擎按主题匹配排序，结合节奏、日期容量、行政区及交通预留进行安排，远郊独立一天。容量不足会显式列出未安排项，不静默丢弃。

后端保存带输入快照、归属和 30 分钟有效期的方案；用户确认后，行程接口检查方案、版本和日程规则，将草稿转换为 planned。后续修改继续走版本与事务保护。真实高德耗时尚未自动参与排程，开放时间及预约仍需核实。
