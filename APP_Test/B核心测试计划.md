## 1. 测试目标与范围

本轮以本人负责的 B 模块为测试驱动开发对象，沿用团队《接口与数据约定》和此前的功能预设，覆盖以下交付：

- 推荐方案保存、归属、输入快照、有效期及重新读取。
- 路线预览、逆地理编码、GPS 转换及服务异常降级。
- 模型排序建议、输出约束、候选重新排程与失败回退。
- 六个公开 HTTP 接口的请求、响应、身份边界和错误处理。

需要同时证明两件事：功能符合需求；开发过程确实由测试驱动，测试先于对应业务实现，代码改进使失败用例逐步通过。

### 1.1 已有代码与初始 0% 如何处理

当前仓库已包含 B 的实现，已有测试也曾通过，不能把历史结果改写成“最初 0%”。计划使用**独立的 TDD 教学分支或工作目录**，从尚未实现本轮业务的可运行骨架开始，保留既有开发成果。

实施前明确并记录：

| 版本         | 用途                                                     |
| ------------ | -------------------------------------------------------- |
| 需求参考版本 | 确定接口、字段、规则及验收预期，避免测试过程中随意改需求 |
| TDD 起始版本 | 具备依赖、测试工具和必要接口骨架，但尚未实现本轮业务逻辑 |
| 测试先行版本 | 核心测试已提交，业务实现尚未开始，用于首次失败运行       |

先确认测试工具能正常执行，再运行初始业务测试。首次通过率必须来自真实结果。若基线已有部分功能通过，就如实记录并核对起点，不能通过删除断言、改错预期或破坏已有成果制造 0%。

## 2. 测试先行的工作流程

采用 Red—Green—Refactor 循环，先提交核心测试集，再进入业务实现；每个阶段内部仍小步迭代。

| 环节            | 计划操作                                       | 完成条件                             | 证据                           |
| --------------- | ---------------------------------------------- | ------------------------------------ | ------------------------------ |
| 准备            | 确定契约、用例清单、测试数据与运行骨架         | 测试可加载执行，环境检查通过         | 起始版本、用例清单、环境记录   |
| Red：先写测试   | 写输入、期望输出和断言，运行尚未实现功能的测试 | 因缺少目标行为而失败，原因符合预期   | 测试提交、失败日志、用例编号   |
| Green：最小实现 | 编写满足测试的业务代码或修复对应缺陷           | 目标用例通过，已通过用例不退步       | 实现提交、完整结果、通过率变化 |
| Refactor：重构  | 改善重复代码、结构、命名和模块边界             | 行为保持，核心测试及既有回归继续通过 | 重构提交、回归记录             |

后续发现遗漏需求或新缺陷时，也先补能够稳定失败的测试，再修改实现。修改测试预期必须有明确的需求依据，不能仅为了提高通过率降低断言强度。

| 用例范围                   | 预期行为                                                         | 方法                     |
| -------------------------- | ---------------------------------------------------------------- | ------------------------ |
| 两天三景点基准流程         | 返回合法日程并覆盖所有选择                                       | 纯函数测试、基准场景     |
| relaxed/standard/intensive | 开始时间、休息和日景点上限符合约定                               | 决策表、节奏参数矩阵     |

| 用例范围                        | 预期行为                                             | 方法                     |

## 5. 通过率与测试结果的统计口径

```text
核心通过率 = 核心集合中通过的逻辑用例数 / 冻结的核心用例总数 N × 100%

初始：0 / N = 0%
最终：N / N = 100%
```

- 一项逻辑用例可含多个断言或多组数据，但不以增加断言数量虚增通过率。
- 非法输入得到正确拒绝，该测试为通过；“测试失败”指实际行为与期望不符。
- 通过、失败、阻塞、跳过分别统计。核心集合中的阻塞和跳过不计通过，也不能移出分母。
- 依赖安装失败、语法错误、测试无法导入或服务未启动，属于环境问题，不作为有效初始 Red 证据。
- lint、类型检查、构建、环境检查和历史回归单列，不混入本轮核心业务通过率。
- 需求变化需要增删用例时，记录清单版本、新旧总数和原因；不得静默删除失败项。
- 达到核心 100% 时，应注明适用用例集和代码版本，避免把有限范围的结论扩大成整个项目全部完成。

## 7. 工具、环境与数据管理

- 单元与性质测试：Node.js `node:test`、`assert`；固定数据、种子和时钟。
- HTTP 测试：实际 NestJS 随机端口和 `fetch`，测试替身只用于隔离外部依赖，不替代被测实现。
- 数据库测试：服务器 Docker 内的 PostgreSQL，专用 `_test` 库和随机 schema；只清理自身数据，不使用本机 Docker。
- 外部适配器：本地 HTTP 测试服务注入成功、失败、慢响应和非法响应。
- 浏览器联合验收：Playwright，保存关键操作截图；不存在的业务页面不以静态样例冒充完成。
- 私有配置：真实 token、数据库连接、服务器密码和 Key 不写入测试代码、提交或报告。

初始阶段先满足环境可运行，再开始统计业务通过率。真实数据库、外部服务和浏览器的运行前提在执行记录中写明。

## 8. Git 提交与阶段证据计划

提交先后顺序应能从版本历史核对。计划按功能小步提交：

```text
test: 增加输入校验测试（预期失败）
feat: 实现输入校验以通过相应用例
refactor: 整理校验代码并保持回归通过

test: 增加下一组测试或缺陷回归（预期失败）
feat/fix: 实现对应功能或修复缺陷
refactor: 保持全部已通过用例行为
```

初始完整核心测试版本早于本轮业务实现版本。每次提交保存对应日志，再按团队要求推送分支和测试材料；不能在实现结束后补造“先测试”的时间顺序。

每轮材料计划保存在 `reports/tdd/<时间>-<阶段>/`，包含用例集版本、源代码 commit、执行命令、完整结果、本轮新增通过用例、对应代码改动，以及必要的 HTTP/模型证据和截图。

## 9. 完成标准

1. 核心用例清单已冻结，每项有唯一编号、输入、预期、方法与需求对应关系。
2. 有效初始运行体现业务未实现时的 0/N，没有用环境损坏或跳过制造 0%。
3. 测试先于对应实现，提交和日志能证明通过率提升来自业务实现或改进。
4. 最终完整运行冻结集合，N/N 通过，核心失败、阻塞和跳过均为 0。
5. 重构后核心测试和既有回归保持通过，lint、类型检查、构建与格式检查通过。
6. 真库、替身和真实外部调用界限清楚，不能把不同依赖的结果混作一条完整生产流程。
7. 测试、代码和阶段资料可复现；尚未完成的 A/C/D 联合流程及正式服务专项另行披露。

本计划用于指导下一轮“先测试、后实现”的开发过程，本次仅更新计划文档。
