# A：前端开发说明

## 1. 你的交付

负责用户能操作的完整应用：登录、首页、城市/日期/偏好/景点四步表单、推荐预览、已保存行程、手账表单与图文详情。D 提供可嵌入的地图组件，你负责把它放进统一页面并接好交互。

先读 [总体架构](总体架构.md)、[接口与数据约定](接口与数据约定.md) 和 [统一示例](examples/README.md)。当前 React 页面仅显示 API 状态；下列页面、路由、模拟客户端和业务请求均需新增。

## 2. 文件放在哪里

```text
apps/web/src/
  App.tsx                         应用布局和路由装配
  components/                     按钮、表单、加载、错误和确认弹窗
  lib/api.ts                      沿用已有入口，扩展统一 HTTP 请求
  lib/api/                        需要拆分时放身份、行程等请求文件
  features/auth/                  注册、登录和身份状态
  features/trip-wizard/           四步表单及草稿状态
  features/trips/                 行程列表、推荐预览、每日安排编辑
  features/journals/              随笔列表、编辑、图片预览和详情
  features/footprints/            D 维护，你只接公共导出组件
  dev/                           假客户端和仅开发可见的测试宿主
```

不要将所有页面继续堆进 App.tsx。现有 `lib/api.ts` 只有健康检查请求，扩展时保持该行为兼容；不要在每个组件里重复拼接 URL、认证头和错误转换。

## 3. 先约定页面入口

以下是路由目标，当前未安装或配置业务路由方案，实际落地由你统一完成。

| 页面          | 建议地址                       | 数据来源            |
| ------------- | ------------------------------ | ------------------- |
| 登录/注册     | `/login`、`/register`          | C                   |
| 首页/行程列表 | `/`、`/trips`                  | C；城市信息来自 B   |
| 新建四步表单  | `/trips/new`                   | B 地点目录 + C 草稿 |
| 继续草稿      | `/trips/:id/edit`              | C                   |
| 推荐预览      | `/trips/:id/preview`           | B 方案 + C 当前草稿 |
| 每日行程      | `/trips/:id`                   | C                   |
| 足迹与手账    | `/footprints`、`/journals/:id` | D                   |

新建入口先选城市，再调用 C 创建草稿。后续步骤保存同一个草稿，避免每次点击下一步都创建新行程。页面内表单状态与服务端已保存状态分开，保存失败不自动前进。

## 4. 最小开发顺序

1. 建公共请求入口和假客户端选择入口，用同一组业务方法调用两者。开发模式可以注入假客户端；正式构建不应默认启用模拟身份或伪造成功。
2. 用统一示例完成城市选择、日期、主题与节奏、景点列表。主题保存编码，界面显示中文；日期包含首尾，同日为一天。
3. 完成预览页：按天展示、展示估算/未核实警告和未安排项。未安排非空时禁止确认，并提供返回修改入口。
4. 确认时只传 `proposalId` 和当前 `expectedRevision` 给 C，不提交整份预览 JSON 当成可信方案。成功后以 C 返回的 Trip 替换本地状态。
5. 完成已保存行程的换日、排序。修改景点集合走选择接口并确认重置；首期 schedule 接口只保存同一组已选景点的重新安排。
6. 接入 D 地图组件、到访表单、随笔和图片。计划完成不能直接点亮地图，必须由用户确认真实到访日期。

已有视觉原型可作为参考，地图组件内部由 D 维护。第一版“插件广场”等尚无业务的入口可保持无跳转，不为此扩张后端范围。

## 5. 独立测试怎么做

### 不依赖后端的测试

使用 [demo-scenario.json](examples/demo-scenario.json) 的 `responses` 作为假客户端返回值。假客户端和真实客户端的方法签名相同，UI 不需要知道数据从哪里来。

至少支持成功、空列表、延迟、失败和版本冲突五种场景；可以由开发入口切换。JSON 不会自动拦截 fetch，需要你编写 `dev/mock-api.ts` 等适配。修改假数据不得影响真实接口语义，例如模拟成功也应递增 revision、保留已输入内容。

| 场景                | 页面必须表现                              |
| ------------------- | ----------------------------------------- |
| 日期倒置/超过 30 天 | 明确提示，不发生成请求                    |
| 前一步保存失败      | 保留输入、不跳到下一步，可重试            |
| 更换城市            | 提示旧景点选择将清空，按 C 返回状态刷新   |
| 推荐有未安排项      | 展示具体地点和警告，禁止确认完整方案      |
| 409 版本冲突        | 提示刷新/重新载入，不能自动覆盖另一次编辑 |
| 410 方案过期        | 保留规划条件，允许重新生成                |
| 401                 | 引导重新登录，不能显示成空行程            |
| 重复点击确认        | 请求期间禁用，避免并行写入                |
| 重新搜索先后返回    | 不让旧请求结果覆盖新关键词结果            |
| 图片上传失败        | 保留文字和其他图片，可重试                |

### 接真实 API

使用 C 返回的身份、B 返回的目录和推荐、D 返回的手账。请求路径默认 `/api`，沿用 Vite 代理，不在代码里写死他人电脑 IP。登录 token 首期仅保存在内存，刷新后可重新登录；恢复登录能力后续单独设计。

上传用 FormData，让浏览器生成 multipart boundary。私人图片通过携带 Bearer token 的 fetch 取得 Blob；使用完释放 object URL。不要在 `<img src>` 的 URL 中塞 token。

## 6. 与 D 的组件交接

目标组件名 `FootprintMap`，属性按 [D 的说明](D-足迹与地图手账开发说明.md) 固定。你提供数据、加载和错误状态，接收地点选中和地图位置选择回调；组件内部不处理登录、跳转或全局请求。

地图 Key 未配置时显示明确的不可用状态，不能因为地图初始化失败导致手账列表也无法使用。D 自己的开发宿主页不能代替你这里的页面整合。

## 7. 启动、检查和交付

从项目根目录运行现有命令：

```powershell
npm ci
npm run dev:web
```

浏览器默认 <http://localhost:5173>。纯假客户端页面无需 PostgreSQL，但当前 API 健康状态页可能显示未连接；在实现开发模式切换前，它仍只是基础页面。不要把“安装依赖并启动 Vite”写成业务页面已经可用。

```powershell
npm run lint
npm run typecheck --workspace=@travel/web
npm run build --workspace=@travel/web
```

当前无前端专用自动化测试脚本。交付时提供关键流程的浏览器验证记录；需要增加自动化时同步补脚本，不能写一个不存在的 `test:web` 命令。至少检查 390 像素手机宽度和 1280 像素电脑宽度，无横向溢出、文字遮挡、不可点击按钮或控制台异常。

完成标准：假客户端下流程完整；真实接口下登录后可保存、刷新重开草稿、确认推荐并读取已保存安排；地图和图文入口可用；附上成功与失败各一组记录。页面截图不能代替真实保存验证。
