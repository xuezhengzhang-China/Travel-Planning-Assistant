# 四人共用示例数据

本目录是静态开发材料，不启动服务器、不创建账号、不插入数据库，也没有实现图片上传。A 为它编写假客户端，B/C/D 可把它读入测试夹具；真实联调仍需业务实现和种子数据。

## 文件

- [demo-scenario.json](demo-scenario.json)：两位测试用户、一个演示省份/城市、三个景点、两天行程请求、草稿/推荐/正式行程及地图手账示例。
- [error-cases.json](error-cases.json)：使用上述数据时的异常前提和预期 HTTP 响应。它是测试设计数据，不是能直接运行的测试脚本。

## 使用方法

1. 资源 ID 固定，四人引用同一个城市和景点，不在自己的模块另造一组不相容 ID。
2. `actors` 只供测试装配注入身份；正式 HTTP 请求中不能提交它来模拟登录。
3. `requests` 是请求体；`responses` 是相应预期资源，不含通用 data 包装。
4. 草稿是四步保存后的快照，revision 为 4；确认相应 proposal 后为 5。不表示中间步骤可以跳过版本检查。
5. `fixedNow` 用于方案有效期测试。真实演示由后端新生成时间；不要把静态过期时间当作线上方案使用。
6. 景点信息、坐标、建议时长和行程时间仅作合成演示。不要据此声称实时路线或开放时间已经核实。
7. 手账记录是另一条真实到访演示，与未来的计划行程分离。两条到访位于同一个城市，适合测试删除最后一次到访的点亮变化。
8. 媒体仅有元数据，没有图片字节。验证上传/授权读取时需准备自己的非私人测试图片，实际执行上传。

## 对照入口

| 负责人 | 优先使用                                                              |
| ------ | --------------------------------------------------------------------- |
| A      | responses、requests、error-cases，编写假客户端与页面状态              |
| B      | destinations、places、recommendationRequest、proposal，校验排程不变量 |
| C      | actors、tripDraft、applyProposal、tripPlanned，验证身份和版本         |
| D      | actors、visitedPlaces、journal、footprints，验证地图聚合与图文关联    |

两天三个景点不规定推荐算法只能输出这一种顺序。示例是一个合法结果，算法测试以日期、唯一性、预算、未安排集合等约束为主；若要逐字段快照比较，应固定适配器、规则、时钟和 ID 生成器。
